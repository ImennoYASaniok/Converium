# Contributing

## Формат коммитов

Используем единый формат сообщений коммитов:

`тип(модуль): описание`

Где:
- `тип` — категория изменения (см. список ниже)
- `модуль` — затронутая область проекта
- `описание` — краткое описание того, что сделано

Пример:
- `feat(frontend): добавил страницу входа в систему`
- `fix(backend): теперь возвращает значение 400 для неверных учетных данных`
- `feat(db): создал индексы для таблицы курсов`

## Типы (`тип`)

Разрешённые значения:
- `feat` — новая функциональность
- `fix` — исправление бага
- `refactor` — рефакторинг без изменения поведения
- `perf` — улучшение производительности
- `docs` — изменения документации
- `test` — тесты
- `chore` — обслуживание проекта (обновления, форматирование, мелкие правки без бизнес-смысла)
- `build` — изменения, влияющие на сборку/пакетирование (Gradle/Vite/Docker сборка)
- `ci` — изменения CI/CD (workflows, pipelines)

## Модули (`модуль`)

Разрешённые значения:
- `backend`
- `frontend`
- `db`
- `infra`
- `deps`
- `config`

Описание модулей:
- `backend` — серверная часть (Spring Boot/Kotlin): контроллеры, сервисы, репозитории, модели, безопасность.
- `frontend` — клиентская часть (Vue/Vite): страницы, компоненты, роутинг, store, стили.
- `db` — изменения, связанные с БД: миграции/схема/индексы/запросы/инициализационные скрипты.
- `infra` — инфраструктура и окружение: Docker/Docker Compose, деплой, конфиги CI окружения, скрипты запуска.
- `deps` — обновление/добавление зависимостей (библиотеки), без изменения логики продукта (когда возможно).
- `config` — конфигурация приложений: `application*.yml`, настройки CORS/JWT, переменные окружения, параметры сборки.

Если изменение затрагивает несколько модулей:
- предпочтительно разбить на несколько коммитов
- если невозможно — используйте `core` или `multi` (выберите один вариант и придерживайтесь его)

## Правила для `описание`

- Одной строкой, без точки в конце.
- Повелительное наклонение (как команда): `add`, `fix`, `remove`, `update`.
- Желательно до 72 символов.
- Язык — русский.

## Примеры

- `feat(backend): реализовал конечную точку входа в систему jwt`
- `fix(frontend): обработал 401 и перенаправил на вход в систему`
- `refactor(backend): разделил обслуживание курсов на уровни`
- `chore(infra): обновил порты docker compose`
- `build(config): обновил параметры сборки`
- `ci(infra): добавил проверку формата коммитов`
- `chore(deps): обновил версии зависимостей`

## Как оформлять серию изменений

- Один коммит = одно логическое изменение.
- Не смешивать форматирование/рефакторинг и функциональные изменения в одном коммите.
- Перед PR убедиться, что история читается сверху вниз.

### Локальный enforcement через `core.hooksPath`

В репозитории лежат хуки в папке `githooks/`.

Включение (один раз на машине разработчика):

```bash
git config core.hooksPath githooks
```

Проверка:
- При попытке сделать коммит git вызовет `githooks/commit-msg`.
- Если сообщение не соответствует формату `тип(модуль): описание`, коммит будет отклонён.

Примечание для Windows:
- Если `commit-msg` не запускается как shell-скрипт, можно использовать `githooks/commit-msg.ps1` вручную или настроить окружение (Git Bash).

## Автоматическая проверка в CI

В репозитории настроена проверка сообщений коммитов через GitHub Actions.

Что проверяется:
- Каждый коммит в PR (и пуши в основные ветки) должен соответствовать формату `тип(модуль): описание`.

Если формат нарушен:
- workflow упадёт,
- PR нельзя будет смержить (если в репозитории включено требование успешных checks).
